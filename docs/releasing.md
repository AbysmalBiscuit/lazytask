# Cutting a release

Releases come from a release PR. You never edit the version, write the changelog, or push a tag by hand.

- [release-please](https://github.com/googleapis/release-please) reads the [Conventional Commits](https://www.conventionalcommits.org) on `master` and keeps a release PR open that bumps the version and updates `CHANGELOG.md`.
- Merging that PR creates the `vX.Y.Z` tag and the GitHub Release.
- [cargo-dist](https://github.com/axodotdev/cargo-dist) builds every target for that tag and attaches the archives and installers to the Release.

## TL;DR

1. Merge work into `master` with conventional commit messages (`feat: ...`, `fix: ...`). PR titles are checked for this format.
2. The `release-please` workflow opens or updates a PR titled `chore(master): release X.Y.Z`.
3. Review that PR's version and changelog, then merge it.
4. The [Releases page](https://github.com/AbysmalBiscuit/lazytask/releases) gets the new version with its archives and installers once the `Release` workflow finishes.

## The pieces

| File | Role |
|---|---|
| [`.github/workflows/release-please.yml`](../.github/workflows/release-please.yml) | Runs on every push to `master`: maintains the release PR, and on its merge creates the tag and GitHub Release |
| [`release-please-config.json`](../release-please-config.json) | release-please settings: Rust release type, version bump rules, `v`-prefixed tags |
| [`.release-please-manifest.json`](../.release-please-manifest.json) | The last released version. release-please updates it in each release PR |
| [`.github/workflows/release.yml`](../.github/workflows/release.yml) | Generated by dist. On a version tag it builds every target and uploads the artifacts to the existing Release; on pull requests it builds every target as a cross-compile check |
| [`dist-workspace.toml`](../dist-workspace.toml) | dist settings: targets, installers, install path |
| `[profile.dist]` in [`Cargo.toml`](../Cargo.toml) | The Cargo profile dist builds with |

`release.yml` is generated. Change `dist-workspace.toml`, then regenerate:

```bash
dist generate
```

dist's CI fails when the workflow and its config disagree, so commit both.

### Token

The `release-please` workflow authenticates with the `RELEASE_PLEASE_TOKEN` repository secret, a personal access token. It cannot use the default `GITHUB_TOKEN`: events caused by `GITHUB_TOKEN` start no workflows, so the tag push would never run the `Release` workflow and the release PR would get no CI.

The secret is not created by any workflow. A maintainer creates it, and the `release-please` workflow fails until it exists:

1. Open the [prefilled fine-grained token form](https://github.com/settings/personal-access-tokens/new?name=lazytask-release-please&description=release-please%20for%20AbysmalBiscuit%2Flazytask&target_name=AbysmalBiscuit&expires_in=366&contents=write&pull_requests=write). It sets the name, the `AbysmalBiscuit` owner, the expiry, and Read and write access to Contents and Pull requests.
2. Under repository access, choose "Only select repositories", then `lazytask`. GitHub cannot prefill this choice. Then generate the token.
3. Store the token as the repository secret. `gh` prompts for the value:

```bash
gh secret set RELEASE_PLEASE_TOKEN -R AbysmalBiscuit/lazytask
```

When the token expires, the workflow fails again. Generate a new one and set the secret again the same way.

## Artifacts

Every Release carries:

| Artifact | Contents |
|---|---|
| `lazytask-installer.sh` | Shell installer for Linux and macOS |
| `lazytask-installer.ps1` | PowerShell installer for Windows |
| `lazytask-<target>.tar.xz` | Linux and macOS archives: the binary, `LICENSE`, `README.md` |
| `lazytask-<target>.zip` | Windows archives, same contents |
| `*.sha256` | One checksum per archive |
| `sha256.sum` | Checksums for every artifact |
| `source.tar.gz` | The source at the tag |

The installers detect the platform, download the matching archive, and put `lazytask` in `$CARGO_HOME/bin` (`~/.cargo/bin` by default).

### Targets

The `targets` list in `dist-workspace.toml` is the source of truth. To see what a release would ship, run:

```bash
dist plan
```

| Platform | Target triple |
|---|---|
| macOS Intel | `x86_64-apple-darwin` |
| macOS Apple Silicon | `aarch64-apple-darwin` |
| Linux x86_64 (glibc) | `x86_64-unknown-linux-gnu` |
| Linux x86_64 (musl, static) | `x86_64-unknown-linux-musl` |
| Windows x86_64 (MSVC) | `x86_64-pc-windows-msvc` |
| Windows x86_64 (MinGW) | `x86_64-pc-windows-gnu` |
| Windows i686 (32-bit) | `i686-pc-windows-msvc` |

To add a target, append its triple to `targets` and run `dist generate`.

## Versioning

LazyTask follows [SemVer](https://semver.org/). release-please picks the bump from the commits since the last release. While the version is below 1.0.0:

| Commits since the last release | Bump |
|---|---|
| `feat:`, `fix:`, `perf:` or `revert:` only | patch (`0.1.0` -> `0.1.1`) |
| A breaking change (`feat!:` or a `BREAKING CHANGE:` footer) | minor (`0.1.0` -> `0.2.0`) |

From 1.0.0 on, `fix:` bumps patch, `feat:` bumps minor, and a breaking change bumps major. Commit types like `docs:`, `chore:`, `ci:` and `test:` do not trigger a release on their own.

To force a specific version, add a `Release-As: X.Y.Z` footer to a commit on `master`.

## Before merging the release PR

The release PR runs the same CI as any other PR, including dist's build of every target. Merge it only when that CI is green and the changelog reads right.

## When a release fails

- **A build job in the `Release` workflow fails on a flake.** Re-run the failed jobs from the workflow run's page. The tag and the Release already exist, so dist uploads to them.
- **A build fails because of the code, or a released version is broken.** Don't delete the tag; clients may already have downloaded it. Mark the GitHub Release as a pre-release or delete only the Release, then fix forward with a `fix:` commit, which opens the next release PR.
